# ADR-0011 — Процесс: plan-driven со спеками, скиллами и DoD

**Статус:** accepted
**Источник:** [constitution](../../plan/constitution.md) P1–P7, R1–R3, `.cursor/rules/*.mdc`
**Связано:** —

## Контекст

Проект ведёт один разработчик вместе с агентами. Контекст задачи должен быть
самодостаточным (агент входит в чат без истории), решения не должны теряться,
релизы должны быть воспроизводимы. Внешние методологии (BMAD, Spec Kit, Kiro) требуют
командных ритуалов и ролей, которых здесь нет.

## Решение

Собственный облегчённый процесс:

- канон — `plan/MVP-PLAN.md` (индекс стадий и шагов), один шаг = один чат;
- шаг — это спека: требования, задачи, тесты, DoD (`templates/step.md`), статусы `planned → draft → approved → in-progress → done`;
- доменные знания — в `plan/skills/<name>/SKILL.md`, расширяются по мере необходимости, а не переписываются;
- найденный дефект сначала попадает в backlog/аудит, затем становится шагом;
- релиз — ритуал ЧКП: CHANGELOG → commit продуктовых файлов → push → тег → release URL.

## Альтернативы

- Внешний SDD-фреймворк целиком — overhead на одного автора, ритуалы под команду.
- Задачи только в GitHub Issues — теряется связка «требование → задача → тест → DoD».

## Последствия

+ Агент получает весь контекст шага из файла и скиллов; решения не утонули в переписке.
+ Появились артефакты, которых не было: конституция и этот ADR (решения отделены от хода работ).
− Индекс и файлы синхронизируются вручную — уже были случаи расхождения (файл без строки в индексе, ссылка без файла).
− Канон лежит вне git (`plan/` не коммитится): нет истории правок и внешнего ревью спеки; ADR тоже не версионируются.
